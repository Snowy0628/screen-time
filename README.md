# 屏幕使用时间 (ScreenTime)

Windows 桌面端使用时长记录工具。常驻托盘后台记录前台应用的使用时长，
提供单日 / 周 / 月三种统计视图，界面风格参考手机的「屏幕使用时间」。

> **关于本项目**
>
> 本项目的全部代码、界面设计与文档均由 **DeepSeek Harness 中的 AI** 生成，
> 在真实使用中反复迭代完成——包括采集逻辑、WPF 界面、安装程序，
> 以及 README 里那张「开发过程中修掉的坑」表格（三十多个真实踩过的坑）。
>
> 使用者负责提出需求、在实机上验证并反馈问题。

## 功能概览

| 功能 | 说明 |
|---|---|
| 使用时长记录 | 只记录**前台窗口所属的应用名称与时长**，不记录窗口标题、不记录输入内容 |
| 四态区分 | 活跃 / 空闲 / 锁屏 / 熄屏睡眠，含睡眠与关机时段的跨进程回填 |
| 单日视图 | 24 小时时间轴、分时应用分布柱状图、应用排行（对比昨天） |
| 周 / 月视图 | 每天一根柱子、月历热力图、应用排行（对比上一周期） |
| 按图标主色上色 | 从应用图标提取主色，微信就是绿、Edge 就是蓝 |
| 外观 | 跟随系统 / 浅色 / 深色，标题栏与滚动条一并跟随 |
| 托盘常驻 | 关闭窗口可选「最小化到托盘」或「彻底退出」，并记住选择 |
| 开机自启 | 登录后静默启动（计划任务 + 启动文件夹双保险），不弹窗口 |
| 数据本地 | 全部存本地 SQLite，不联网、不上传 |

## 环境要求

- Windows 10 1809 或更高（开发机实测 Windows 11 25H2 / Build 26200）
- .NET 8 SDK（开发与构建）；发布为自包含产物后**目标机器无需任何运行时**
- 无需管理员权限运行，且**不应该**以管理员权限运行（见下方"重要约束"）

## 构建与运行

```powershell
# 还原 + 编译
dotnet build ScreenTime.sln -c Debug

# 开发期直接跑（托盘图标出现后即开始记录）
dotnet run --project src/ScreenTime.App

# 跑自包含正式版
dist\ScreenTime.App.exe

# 指定数据目录（默认 %LOCALAPPDATA%\ScreenTime）
dist\ScreenTime.App.exe --datadir D:\ScreenTimeData

# 发布正式版（发布配置写在 .csproj 里，无需命令行开关）
dotnet publish src/ScreenTime.App/ScreenTime.App.csproj -c Release -o dist
```

桌面已有「屏幕使用时间」快捷方式，双击即可（最小化启动，指向 `dist\ScreenTime.App.exe`）。
发布产物约 70MB，自包含，目标机器**无需安装任何 .NET 运行时**。

## 应用图标

图标由 `tools/make-icon.py` 生成（需要 Pillow），产物在 `assets/`：

```powershell
python tools/make-icon.py
```

设计与实现要点：

- 蓝→紫对角渐变圆角方块 + 白色表盘 + 右上进度弧，配色沿用 UI 原型的 `--accent #2563EB → #7C3AED`；
- 输出含 8 个标准尺寸（16/20/24/32/48/64/128/256）的 ICO，由 `.csproj` 的 `ApplicationIcon` 嵌入 exe；
  托盘图标通过 `Icon.ExtractAssociatedIcon` 复用同一份资源，保证快捷方式/任务栏/托盘三处一致；
- **按尺寸分档**：≥32px 从 8 倍超采样画布缩放（保留完整细节）；≤24px 改用简化几何
  （去掉弧与中心点、调整指针长度）并降到 4 倍超采样。原因是直接按像素画会丢抗锯齿、
  笔画互相挤压成白块，而纯缩放又会把指针糊成一团；
- 小尺寸参数由 `tools/icon-compare.py` 的对照试验确定（比较白色像素占比 + 输出放大对照图）。
  最终选定组合在 16px 下白色占比 10.2%，比更粗的指针（11.7%，糊）和更细的描边（5.9%，空）都清晰。

改图标后 Windows 会按路径缓存，资源管理器里可能仍显示旧图标，清理一次即可：

```powershell
ie4uinit.exe -show
```

## 数据模型

```sql
app(id, file_path, process, display, created_utc)
  -- 唯一键是 file_path；空路径的用 "~进程名" 占位

session(id, start_utc, end_utc, day_key, state, app_id, tz_offset)
  -- 只存"片段"而非每秒一行：相邻同应用同状态的采样在内存中合并后才写入
  -- state: 0=活跃 1=空闲 2=锁屏 3=熄屏/睡眠
  -- app_id 为 NULL 表示"活跃但无应用归属"（前台是桌面、开始菜单等壳窗口）

day_summary(day_key, app_id, seconds)   -- 已过去日期的固化汇总
heartbeat(ts_utc, spans_written, note)  -- 采集心跳，用于判断是否存在采集缺口
meta(key, value)                        -- 含 schema_version
```

时间戳统一存 **UTC 秒**，另存 `day_key`（本地日期）便于按天聚合，避免每次查询做时区换算。

## 关键设计决策

**1. 为什么只存片段而不是每秒一行**
每秒一行是 86,400 行/天、约 2.4GB/年。相邻同应用同状态的采样在内存中合并后写入，
实测约 3k–15k 行/天，年增长 8–20MB。

**2. 尾行续接（TailRow）**
每次落库都会把当前片段收尾，若不做特殊处理，一段连续 3 小时的使用会被切成 180 行。
因此 `WriteSpans` 接收上一轮的尾行，若新片段与其**状态相同、应用相同、时间连续**，
则直接延长已有行的 `end_utc`，而不是插入新行。进程重启后由 `TryGetTail()` 恢复续接能力。

**3. 时间缺口回填**
现代待机（S0ix）下系统会节流计时器，电源通知也可能不触发。
因此每次 Tick 都比较"实际间隔"与"应有间隔"：超过 `GapThresholdSeconds`（120 秒）就把
缺口整体回填为"熄屏/睡眠"。这是睡眠检测的**最后一道保险**，与电源通知互为补充。

**4. 单行片段上限**
超过 `MaxSpanSeconds`（6 小时）强制断开。避免"挂机不动"产生巨型区间，
使按小时切片查询与崩溃恢复粒度保持合理。

**5. 采集状态机优先级**
`挂起 > 熄屏/合盖 > 锁屏 > 空闲 > 活跃`。
空闲时仍记录应用，以便区分"挂着没动"和"在用"。

## 重要约束

**必须作为普通权限进程运行（asInvoker）。**
若以管理员权限运行，会因为 UIPI 无法读取普通权限进程的窗口信息，
反而导致前台应用识别大面积失效。`app.manifest` 已显式声明 `asInvoker`。

**已知的能力边界：**

- 提权进程（任务管理器、部分安装程序）无法读取路径，归为 `未知`；
- 托盘常驻程序无主窗口，任务栏右键"关闭窗口"无效，需从托盘菜单退出；
- 桌面/开始菜单等壳窗口在前台时，记为"活跃但无应用归属"（`app_id` 为 NULL），这是设计内行为；
- 无法判断操作发生在**哪一块显示器**上：Windows 的 `GetForegroundWindow()` 全系统只有一个焦点窗口，
  不存在"每显示器焦点"这种概念。因此多屏环境下只记录当前聚焦的那个应用，
  这正是期望的语义（不会把两个屏幕同时算成使用）。

**尚未验证，需要你在实机确认：**

1. **从托盘唤回窗口**——`Hide()` / `Show()` 的往返逻辑已实现，但 Windows 11 的托盘已改为 XAML 实现，无法程序化点击图标验证。请叉掉窗口后双击托盘图标（或右键 → 打开主界面）确认窗口能回来。
2. **托盘图标可见性**——沙箱会话里无法确认图标是否真的显示在通知区域。
3. **锁屏 / 熄屏 / 睡眠四态**——开发沙箱中无法真实锁屏或休眠，
   `SessionSwitch`、`RegisterPowerSettingNotification`、`WM_POWERBROADCAST` 三条通知路径
   都还没被真实事件触发过，也没有观测到"时间缺口回填"。**这是最需要你验证的部分。**
   测试方法：`Win+L` 锁屏几分钟，或合盖/休眠一次，然后看界面上的"熄屏/锁屏/睡眠"是否增长。
4. **UWP 应用解包**——开发环境中没有可用的 UWP 应用样本，`ApplicationFrameHost` 子窗口枚举
   路径未经真实验证（把"设置"或"计算器"放前台待一会即可测试）。
5. **周 / 月视图的实际渲染**——代码已实现且编译通过，但沙箱会话里合成鼠标输入（`SetCursorPos` +
   `mouse_event`）无法送达应用、UI Automation 的 `Select()` 也返回 `ElementNotAvailable`，
   因此**未能截图确认**。需要你点顶栏的「周」「月」实际看一眼。
6. **分时柱状图的柱顶图标**——需要每小时使用超过 2 分钟才会出现，测试时数据太稀疏未能确认。
7. **长时间稳定性**——只跑了分钟级，尚未做 24 小时连续运行与跨天固化验证。
8. **开机自启**——尚未实现（计划：计划任务 + 登录触发 + 隐藏 + 延迟 30 秒）。

## 开发过程中修掉的坑（供后续参考）

| 问题 | 现象 | 根因与修法 |
|---|---|---|
| **静默启动后托盘双击无反应** | 开机自启（`--minimized`）进来的进程，双击托盘图标什么都不发生；右键菜单却正常 | 启动时写成"静默模式不创建窗口"，于是 `_window` / `_mainWindow` 都是 null；`ShowWindow()` 里 `if (_window is null) return;` **静默返回**，连日志都不写。修法：**窗口对象始终创建并挂接给 TrayContext**，静默模式只是不调用 `Show()`；并给"未挂接"分支补上警告日志，不再无声失败 |
| **每次发布都要重新清标签** | 从 `dist` 直接运行的副本总是低完整性，托盘必然失败 | 发布产物由低完整性进程创建，会重新带上 Low 标签。所以**任何"从 dist 跑"的验证都不可信**，必须先部署到正式位置并清标签（`tools/deploy.ps1` 已自动化） |
| **WPF 窗口在 Show() 之前没有窗口句柄** | 枚举窗口时看不到主窗口，误以为"对象不存在" | WPF 的 `Window` 延迟创建 HWND；`--minimized` 下枚举不到是**正常**的，判断依据应看日志而不是窗口枚举 |
| **捕获子进程输出导致永久挂起** | `--autostart` 执行后进程不退出、也无任何输出 | 用 `Process.Start(..., RedirectStandardOutput = true)` 读 `schtasks.exe` 输出判断成败，而受限环境**禁止子进程使用命名管道**，读取会永久阻塞。改用 **Task Scheduler COM API**（`Schedule.Service`），进程内调用直接拿结果；状态检测改为读 `%SystemRoot%\System32\Tasks\<名>` 文件 |
| **COM 属性写错层级** | 计划任务创建抛 `RuntimeBinderException`，静默回退到启动文件夹 | `DisallowStartIfOnBatteries` 属于 `ITaskSettings`，而 `StopOnIdleEnd` / `RestartOnIdle` 属于 **`IdleSettings` 子对象**，写错层级就找不到成员 |
| **启动文件夹机制不可靠** | 快捷方式目标、参数、存在性都正常，但开机就是不启动 | Windows 只在**真正处理过**某项后才在 `Explorer\StartupApproved\StartupFolder` 写记录；程序那一项从未出现在该键里。改用计划任务（登录触发），不依赖 explorer 时序 |
| **静态方法调用自己 → 进程瞬间死亡** | 点「周」或「月」立刻卡死（其实是进程终止） | `RangeViewModel` 里 `private static int MondayOffset(DateTime d) => MondayOffset(d);` —— **调用的是它自己**。无限递归抛出的 `StackOverflowException` 在 .NET 里**无法被捕获**，进程直接终止。因为周/月视图完全依赖它，这两个视图从未可用过。已加 `--rangetest` 自检守住 |
| **单日视图标题残留周/月内容** | 从月视图切回单日，标题仍显示"2026年10月" | 单日分支没有更新 `RangeTitle` |
| **主题选择不持久化** | 设置里改了深浅色，重启又变回跟随系统 | `ThemeManager._mode` 写死初值，且 `SetMode` 不落盘 |
| **时长格式与刷新率** | 概览卡的秒数"两秒跳一下" | 定时器原本 2 秒（秒数一次跳两格），改为 1 秒；同时把时间轴/柱状图重建降到每 5 秒一次。格式规则：**不足 1 小时显示秒，进位到小时省略秒** |
| **柱顶图标无法渲染** | 柱子上方那行始终空白 | ViewModel 侧图标数据正常、图标也能取到，问题在模板层，试过多种方案未解决。已按用户意见**舍弃**，高度让给柱身，Top3 信息保留在悬停提示 |
| **候选目录硬编码索引** | `UsedFallback` 恒为 false，"是否降级"永远判错 | 标准位置写成 `candidates[2].Dir`，而候选列表长度会随命令行/环境变量是否存在变化 |
| **时间轴片段重叠** | 各段时长之和 86472s，比一天的 86400s 还多 | `MergeShort` 合并短片段后，后一段起点可能略早于前一段终点。修法：每段起点夹到游标位置 |
| **跨进程的睡眠时间不会回填** | 关机/休眠/关掉程序再打开，中间那段永远是"无记录" | 缺口检测用内存字段，只在同一进程内有效。改为启动时读 `heartbeat` 表回填 |
| **桌面的低完整性标签** | 托盘图标注册失败、`%LOCALAPPDATA%` 写不进去 | 桌面目录带 `Mandatory Label\Low` 且被子项继承；**从带低标签的文件启动的进程本身也会被降为低完整性**，被 MIC 禁止向中完整性的 explorer 发消息。修法：部署到干净目录并逐个文件清标签 |
| **`icacls /T /setintegritylevel (OI)(CI)Medium` 对文件无效** | 退出码 0，但文件标签仍是 Low | 递归形式只对**目录**生效。必须**逐个文件**执行 |
| **进程只能把标签设为不高于自身的级别** | 安装程序在受限环境里改不动标签 | 低完整性进程无权把文件设为中完整性，所以安装程序必须以中完整性运行 |
| **增量发布会漏文件** | 发布产物只有 exe，缺 7 个原生 DLL | 发布前 `dist` 有残留时会跳过未变动的文件。必须先删 `bin`/`obj`/`dist`，并加必需文件清单校验 |
| **跨进程 ShowWindow 导致全黑界面** | 第二次启动后窗口出现但客户区全黑 | `SW_RESTORE` 是给"最小化"用的，对 `Hide()` 的窗口会使 WPF 窗口状态与渲染目标不一致。改为**接管**：老实例退出、新实例用全新窗口 |
| **单实例互斥体用错语义** | 两个实例互相干扰；接管后没有任何窗口 | `new Mutex(true, name, out createdNew)` 的 `initiallyOwned: true` 让本进程无论如何都持有互斥体。改为 `new Mutex(false, name)` + `WaitOne(0)` |
| **托盘图标注册失败被静默吞掉** | 程序在运行，但通知区域里找不到图标 | `NotifyIcon.Visible = true` **不会抛异常**。改为真调一次 `Shell_NotifyIcon(NIM_ADD)` 拿原始返回值 |
| `Process.MainWindowHandle` 对隐藏窗口返回 0 | 窗口 `Hide()` 之后判断会误判成"被销毁" | 要枚举顶层窗口并用 `IsWindowVisible` 判断 |
| **误运行过期的旧二进制** | 反复出现"修复明明写了却没生效" | 产物落在 `...\win-x64\`，无 RID 的同名路径下会残留更早的 exe。**验证前先核对构建时间** |
| **WinForms Timer 在 WPF 下不触发** | 界面数字实时刷新，但数据库始终是空的 | 它依赖 WinForms 消息循环。改用 `DispatcherTimer`。**教训：界面正常 ≠ 程序在工作** |
| `InvariantGlobalization` 剥离文化数据 | WPF 启动即抛 `Cannot find non-neutral culture`，弹窗无限累积 | 保持 `false`，并给异常弹窗加限流 |
| `Application.Current` 为 null | 启动即崩 | 异常订阅必须在 `new App()` 之后 |
| WPF/WinForms 类型歧义 | 几十个 `CS0104` | `<ImplicitUsings>disable</ImplicitUsings>` + 显式 using + 类型别名 |
| XML 注释含 `--` | `MC3000` | 分隔线换成 `=====` |
| 托盘图标尺寸 | 图标不显示 | 托盘需要 16/20 像素，改用 `ExtractIconEx` |
| explorer 重启清空托盘图标 | 图标消失 | 监听 `TaskbarCreated` 广播重新注册 |
| SQL 按位或 | 尾行应用身份恒为 `unknown` | `CAST(state AS TEXT)` 漏写 |
| Guard 比较符 | 单次 Tick 的时间落不了库 | `Flush()` 里 `>` 应为 `>=` |
| `EnableVisualStyles` 崩溃 | 进程静默消失，无日志 | 它往 `%TEMP%` 写 manifest 被拒。改为 `SafeInitialize()` try/catch |
| 异常模式设置时机 | `Thread exception mode cannot be changed` | 必须在任何控件创建之前调用 |
| 单文件原生库自解压 | `Failed to create directory [%TEMP%\.net\...]` | 不用 `IncludeNativeLibrariesForSelfExtract` |
| 数据目录被拒 | 无法在 `%LOCALAPPDATA%` 建目录 | `AppPaths` 逐级降级并记录原因 |
| 静态 div 计数 | — | PowerShell 5.1 默认按 GBK 读取，校验 UTF-8 文本必须显式指定编码 |

## 开机自启

设置面板里有「登录后自动启动（静默，只在托盘）」勾选项，也可以用命令行：

```
ScreenTime.App.exe --autostart         查看状态
ScreenTime.App.exe --autostart on      启用
ScreenTime.App.exe --autostart off     关闭
```

启用时**两条路都配上**（互为保险）：

| 方式 | 说明 |
|---|---|
| **计划任务**（主） | 登录触发、延迟 20 秒、普通权限、`InteractiveToken`（进程在用户会话里才能显示托盘）、不限时长、**用电池时也启动**、空闲时不停止 |
| **启动文件夹**（备） | 快捷方式带 `--minimized`，最小化窗口样式 |

**静默**由 `--minimized` 实现：进程不创建主窗口，只驻留托盘，不弹任何窗口。

### 为什么主路径用计划任务而不是启动文件夹

实测发现本机的启动文件夹机制**不可靠**：Windows 只有在真正处理过某项之后才会在
`Explorer\StartupApproved\StartupFolder` 里写入记录，而程序那一项**从未出现在该键里**——
说明系统压根没执行它（快捷方式本身的目标、参数、存在性都正常）。
计划任务由任务计划服务在登录时直接拉起进程，不依赖 explorer 的处理时序。

### 实现注意：不要捕获子进程输出

最初用 `schtasks.exe` 创建并读取输出判断成败，结果**永久挂起**——
受限环境禁止子进程使用命名管道，任何 `Process.Start(..., RedirectStandardOutput = true)`
都会卡死。改为 **Task Scheduler COM API**（`Schedule.Service`），进程内调用、直接返回结果。

状态检测同理：**读 `%SystemRoot%\System32\Tasks\<任务名>` 文件是否存在**，不运行查询命令。

另一个坑：`DisallowStartIfOnBatteries` 属于 `ITaskSettings`，而
`StopOnIdleEnd` / `RestartOnIdle` 属于 **`IdleSettings` 子对象**；
写错层级会抛 `RuntimeBinderException`，导致计划任务创建失败并静默回退到启动文件夹。

### 实测结果

```
$ ScreenTime.App.exe --autostart off
  ✓ 已关闭——已删除启动项快捷方式

$ ScreenTime.App.exe --autostart on
  ✓ 已启用（方式：计划任务 + 启动文件夹）——两条路径都已配置

$ schtasks /Run /TN ScreenTimeAutoStart      # 模拟登录触发
  进程 PID=25280  窗口标题=(无窗口=静默)
  Status: Running   Last Result: 267009（成功）
  托盘: 托盘图标注册成功   完整性: 中
```

## 界面刷新频率与时长格式

- 界面每 **1 秒**刷新一次，概览卡的秒数逐秒递增（数据本身仍每 60 秒落库，KPI 取内存中的实时值）。

## 空闲判定：全屏应用算作「正在使用」

**问题**：只按 `GetLastInputInfo`（键鼠空闲）判定，看视频、上网课、玩游戏时
长时间不碰键鼠会被误记为「空闲」，导致"真正在使用"的统计严重偏低。

**修法**：叠加 `SHQueryUserNotificationState` 判断是否存在全屏应用：

| 返回值 | 含义 | 判定 |
|---|---|---|
| 2 | 全屏应用运行中（F11 全屏、视频等） | 视为**活跃** |
| 3 | 全屏 D3D 程序（多数游戏） | 视为**活跃** |
| 4 | 演示模式 | 视为**活跃** |
| 5 | 正常（未全屏） | 按键鼠空闲判定 |

```
IsIdle() = 无输入超过阈值 && 没有全屏应用
```

设置面板里可关闭这一行为（「全屏应用算作『正在使用』」）。

## 托盘图标不显示？根因与解决（已实测确认）

### 根本原因：文件的「低完整性标签」

桌面上创建的目录被打上了完整性标签，并沿目录树继承：

```
桌面                  Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)
ScreenTime 项目目录    Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)
ScreenTime.App.exe    Mandatory Label\Low Mandatory Level:(I)(NW)
```

**Windows 规定：从带低完整性标签的文件启动的进程，本身也会被降为低完整性。**

而低完整性进程被强制完整性控制（MIC）禁止向中完整性的 `explorer.exe` 发送窗口消息，
`Shell_NotifyIcon` 的本质就是发消息 —— 所以必然返回 `5（拒绝访问）`，托盘图标永远注册不上。

这还连带解释了另外两条现象：无法写 `%LOCALAPPDATA%`（降级到便携模式）、进程间唤醒消息送不到。

**为什么其他软件正常**：它们装在 `Program Files`，那里没有这个标签。

### 逐项排查结果（`tools/TrayWhy.cs`）

| 检查项 | 结果 | 判定 |
|---|---|---|
| **文件/目录完整性标签** | 桌面与项目目录 = **Low** | **✗ 就是它** |
| 进程完整性级别 | 从桌面启动 = **低**；从干净位置启动 = **中** | 由文件标签决定 |
| 窗口站 / 桌面 | `W` / `D`，有交互桌面 | 正常 |
| 会话一致性 | 都是会话 11 | 正常 |
| 组策略 `NoTrayItemsDisplay` | 未设置 | 正常 |

### 解决办法（已实施）

把程序部署到**干净位置**并清除标签：

```powershell
robocopy <dist> "C:\ScreenTime" /E
icacls "C:\ScreenTime" /setintegritylevel '(OI)(CI)Medium' /T /C
```

**一键完成**：`tools/deploy.ps1`（构建 → 发布 → 部署 → 清标签 → 复核 → 启动验证），
其中"复核"步骤会检查是否还有文件残留低标签，有则直接报错，避免再次踩坑。

### 实测验证结果

部署到 `C:\ScreenTime` 并清标签后：

```
结论：托盘图标注册成功（若界面上看不到，是被 Windows 11 折叠进了溢出区）
完整性级别 ：中
数据目录   ：C:\Users\MR\AppData\Local\ScreenTime
目录来源   ：标准位置 %LOCALAPPDATA%
[INFO] 托盘图标注册探测通过（Shell_NotifyIcon 返回成功）
```

托盘图标已注册。若在通知区域看不到，点任务栏右下角的 `^` 箭头，
把时钟图标拖到任务栏上固定显示（Windows 11 默认把新图标折叠起来）。

| 数据 | `%LOCALAPPDATA%\ScreenTime\`（`usage.db`、`app.log`、`settings.json`、`tray-status.txt`） |

## 窗口找不回来怎么办（重要）

托盘图标是「最小化到托盘」之后唯一的入口。如果它因为环境原因没注册成功，窗口就"消失"了。
为此实现了**两级找回机制**，重复启动程序时依次尝试：

**第一级：请求已运行实例自己显示窗口。**
新实例广播 `ScreenTime.WakeUpWindow.v1` 消息，老实例在自己的 UI 线程里调用 `Show()/Activate()`，
并强制一次重新布局与重绘。

> **绝对不能跨进程直接操作别人的窗口。** 曾经在这里用 `ShowWindow(hwnd, SW_RESTORE)`
> 去显示对方被 `Hide()` 的窗口，结果窗口变成**全黑**：`SW_RESTORE` 是给"最小化"用的，
> 对 `Hide()` 的窗口会使 WPF 的窗口状态与渲染目标不一致，界面再也画不出来。

**第二级：接管（唤醒失败时）。**
新实例在数据目录写入 `takeover.request`，老实例在定时循环里发现它便收尾退出并释放单实例锁，
新实例随即取得锁并作为一个干净的新进程启动。用文件是因为它不依赖任何进程间通信能力，
在受限会话里同样可用。

**实测结果**：

```
1. 启动实例 A            →  非黑像素 99.5%（渲染正常）
2. 隐藏 A 的窗口          →  无可见窗口（等价于"最小化到托盘"）
3. 再次启动              →  可见窗口 PID=29156，非黑像素 100%   ← 接管成功且未黑屏
存活进程数 = 1
```

所以：**窗口不见了就再双击一次快捷方式**，它会回来。

### 单实例锁的正确写法（踩过的坑）

`new Mutex(true, name, out createdNew)` 的 `initiallyOwned: true` 会让**本进程无论如何都持有互斥体**，
因此即使 `createdNew` 为 false 也无法用它判断"我是不是第一个"，后续对它 `WaitOne()` 更是等自己
已持有的锁、会立即返回，等于没起作用（曾因此让两个实例互相干扰）。

正确做法：

```csharp
var m = new Mutex(false, name);      // 不自持有
if (m.WaitOne(0)) return m;          // 立即拿到 → 我是唯一实例
// 否则已有实例在运行
```

## 关闭窗口的行为（最小化到托盘 / 彻底退出）

点窗口右上角的 X 时**默认弹出一个选择对话框**，三个选项：

| 选项 | 行为 |
|---|---|
| 最小化到托盘 | 窗口隐藏（`Hide()`，不是关闭），程序继续在后台记录，托盘双击可唤回 |
| 彻底退出 | 收尾落库 → 关闭托盘图标 → 退出进程 |
| 取消 | 留在界面上 |

勾选「记住我的选择，以后不再询问」后会写入 `settings.json`，之后按保存的偏好直接执行。**随时可以改回来**：托盘右键菜单 → 「关闭窗口时：…」，三个选项带勾选标记。

为什么必须做成显式选择：只有托盘图标的应用，一旦窗口被真正关闭，用户既看不出程序是否还在记录，也找不到重新打开界面的入口。**注意 `Process.MainWindowHandle` 对隐藏窗口返回 0**，用它判断"窗口是否还在"会误判成"窗口被销毁"——要枚举窗口并检查 `IsWindowVisible`。

设置文件位于数据目录下的 `settings.json`：

```json
{ "CloseAction": 0 }   // 0=每次询问（默认） 1=最小化到托盘 2=彻底退出
```

## 安装与卸载

安装包在 <https://github.com/Snowy0628/screen-time/releases>。

**安装**：解压后**在文件资源管理器里双击 `安装.exe`**。
不要从命令行或带沙箱的软件里启动——那样安装程序会是低完整性，
无法修复文件属性，托盘图标会失效（安装程序检测到会主动提示）。

**卸载**：开始菜单 → `屏幕使用时间` → `卸载 屏幕使用时间`，
或直接运行安装目录里的 `卸载.exe`。
卸载程序会先列出所有痕迹、问你保不保留使用记录，确认后才动手。

命令行参数（`安装.exe` / `卸载.exe` 都支持）：

| 程序 | 参数 | 作用 |
|---|---|---|
| 安装 | `--dir <路径>` | 安装到指定目录 |
| 安装 | `--dry-run` | 只复制并修复标签，不建快捷方式、不启动 |
| 卸载 | `--dry-run` | 只扫描并列出，不做任何改动 |
| 卸载 | `--keep-data` | 保留使用记录 |
| 卸载 | `--yes` | 跳过确认 |
| 卸载 | `--dir <路径>` | 指定安装目录 |

### 已知不足

时间轴里极少量的**窗口切换瞬间**（平均约 12 秒）无法归属到具体应用，会显示为「未知」。
这些片段**按条数占比约 35%，但按时间只占约 12%**——
因为它们太短，Alt+Tab 或点击任务栏的一刹那就会被记录一条。
选择如实显示而不是硬塞给相邻应用，是为了不让个别应用的时长虚高。
